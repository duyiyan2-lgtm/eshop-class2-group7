# C03 订单超时自动取消 — 现场演示脚本

> 日期：2026-07-29
> 适用：验收答辩 5～8 分钟边界演示
> 实现位置：`OrderTimeoutScheduler` + `OrderService` 条件更新

## 一、原理一句话

待支付订单超过配置分钟数后，定时任务扫描并用 **数据库条件更新** 将状态从 `PENDING_PAYMENT` 改为 `CANCELED`，成功后才回补库存；与支付接口的条件更新互斥，保证「取消与支付同时发生」时只会成功一个。

## 二、演示前配置

编辑 `eshop-release-v1.0/.env`（**演示结束后改回 30**）：

```env
ORDER_TIMEOUT_ENABLED=true
ORDER_TIMEOUT_MINUTES=2
ORDER_TIMEOUT_SCAN_DELAY_MS=15000
ORDER_TIMEOUT_INITIAL_DELAY_MS=5000
```

重启后端使配置生效：

```powershell
Set-Location 'C:\Users\duyiyan\Desktop\eshop-class2-group7\eshop-release-v1.0'
docker compose up -d --build backend
```

| 变量 | 演示建议 | 生产/日常 |
|------|----------|-----------|
| ORDER_TIMEOUT_MINUTES | 2～5 | 30 |
| ORDER_TIMEOUT_SCAN_DELAY_MS | 15000 | 60000 |

## 三、演示路径 A：超时自动取消 + 库存回补

1. 登录买家账号，记录某 SKU 当前库存（商品详情或后台商品）。
2. 加购 1 件并提交订单，**不要支付**。
3. 打开订单详情：状态为「待支付」。
4. 等待超过 `ORDER_TIMEOUT_MINUTES` + 一轮扫描间隔（约 2～3 分钟）。
5. 刷新订单：状态变为「已取消」；状态日志含超时取消原因。
6. 再看库存：应回补到下单前数量。
7. 对该已取消订单点支付：应失败（业务码约 `40912` / 支付过期相关）。

## 四、演示路径 B：支付与取消冲突（口述 + 可选实测）

**口述要点（必会）：**

- 支付：`UPDATE orders SET status='PAID' WHERE id=? AND status='PENDING_PAYMENT' AND created_at > 截止时间`
- 取消：`UPDATE orders SET status='CANCELED' WHERE id=? AND status='PENDING_PAYMENT' AND created_at <= 截止时间`
- 两个事务竞争时，只有一个 `UPDATE` 影响行数 = 1；另一个为 0，不回补或不支付。
- 多实例扫描同样依赖条件更新，不会重复回补库存。

**可选实测：** 将超时调为 2 分钟，在临界点附近点支付；结果要么支付成功（不取消），要么已取消（支付失败），不会出现「已支付又回补库存」。

## 五、答辩常问

| 问题 | 回答要点 |
|------|----------|
| 为什么用定时扫描而不是延迟队列？ | 课程体量下实现简单、易部署；配置化间隔与批量大小 |
| 如何防重复回补？ | 先条件更新状态成功，再回补；第二次更新 0 行直接跳过 |
| 多实例安全吗？ | 状态机条件在数据库，不依赖单机锁 |
| 与用户手动取消关系？ | 手动取消同样走状态条件与回补，已取消不能再付 |
