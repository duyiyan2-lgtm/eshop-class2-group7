## 一、项目概况

E-Shop 是一个前后端分离的 B2C 电子商城，交付 PC 消费者端、手机 H5 消费者端和 Web 管理端。三端共用 Spring Boot API 和 MySQL 数据库，以 Docker Compose 作为演示运行方式。

系统已经打通“注册/登录 → 商品与 SKU → 购物车 → 地址 → 下单 → 模拟支付 → 后台发货 → 确认收货 → 评价”的完整流程，同时实现收藏、浏览历史、评价晒图、操作日志、运营统计等扩展，并以 C03“订单超时自动取消”作为主挑战模块。

## 三、技术总结

### 3.1 为什么选择当前技术栈

- Vue 3 + Vite 能在一个工程中维护三端路由，复用 API 和业务模型。
- Element Plus 适合 PC 商城和后台表格表单，Vant 适合手机浏览器 H5，满足“三端”而无需原生 App。
- Spring Boot 将 Web、安全、校验、事务和健康检查统一起来，适合快速构建规范 REST API。
- MyBatis-Plus 减少 CRUD 样板，同时允许统计、库存等关键 SQL 手写和解释。
- MySQL 关系模型适合订单、库存和状态；Flyway 让 V1～V7 的表结构变化可追踪。
- JWT 让三端共享无状态登录，BCrypt 保障密码不明文存储。
- Docker Compose 统一 MySQL、后端和前端环境，Nginx 负责静态资源、SPA 刷新和 `/api` 反向代理。

### 3.2 关键难点与解决方案

#### 难点 1：下单不能超卖

- 问题：如果先查询库存再普通更新，两个并发请求都可能读到库存充足。
- 方案：在事务中执行 `stock >= quantity` 的条件更新，以受影响行数判断扣减是否成功。
- 效果：库存不足时订单整体回滚，不产生负库存和半成品订单。

#### 难点 2：支付和超时取消竞争

- 问题：订单刚超时时，用户支付和定时任务可能同时修改订单。
- 方案：支付和取消都使用“当前状态必须是待支付”的条件更新竞争状态转换；取消方只有更新成功才回补库存。
- 效果：最终只有支付或取消一种结果，重复扫描不会重复回补。

#### 难点 3：商品变化不能影响历史订单

- 问题：商品改名、改价、下架后，如果订单实时关联商品表，历史订单会变化。
- 方案：订单项保存商品名、SKU 规格、图片、成交价和小计快照。
- 效果：历史订单展示和金额可追溯。

#### 难点 4：三端和多人协作容易反复冲突

- 问题：多人同时修改路由、HTTP 封装和 Flyway 会造成冲突，完整目录交付还会覆盖新代码。
- 方案：先冻结接口和表结构；公共文件由组长统一修改；业务负责人交精简差异；合并后统一运行测试和构建。
- 效果：组员页面和扩展能够逐项审查，旧 Mock 和旧路由没有进入最终基线。

#### 难点 5：评价晒图兼容旧数据

- 问题：已有文字评价不能因新增图片字段失效。
- 方案：V7 只新增可空 `images_json`；响应层把空值解释为空数组；限制最多 3 张且只接受系统上传 URL。
- 效果：旧评价继续显示，新评价可在 PC/手机/后台统一展示图片。

### 3.3 典型缺陷及改进

| 缺陷 | 根因 | 修复 |
|------|------|------|
| 匿名 `/auth/me` 曾返回 500 | `/auth/**` 被整体公开 | 仅公开注册/登录，其余要求 JWT |
| MySQL 8.4 JDBC 连接失败 | 默认认证需要公钥获取参数 | 数据源 URL 增加可配置参数 |
| 购物车角标不及时更新 | 页面间没有统一通知 | 增加角标刷新事件和请求序号保护 |
| 评价 SQL 在真实库报错风险 | 使用关键字别名 | 改用安全别名并在 H2/MySQL 回归 |
| IIS 访问 `/pc` 404 | 实际访问了 80 端口而非 Nginx 8088 | 固定入口 `localhost:8088`，Nginx 配置 SPA 回退 |
| 组员交付自动 Mock | 请求失败后切换固定数据 | 拒绝合入，所有页面只使用真实 API |
| 评价 4 图返回通用错误码 | DTO 与业务层重复校验 | 统一到业务层，稳定返回 `40033`/`40034` 并补回归 |
| 全量测试偶发 H2 重复建表 | 不同测试上下文共用内存库名 | 使用独立 H2 数据库与上传目录隔离 |

### 3.4 可复用经验

1. 接口和数据库版本越早冻结，后期三端接入返工越少。
2. 状态机和条件更新比只在页面禁用按钮更可靠。
3. 自动化测试负责快速业务回归，真实 MySQL 冒烟负责发现方言、迁移和容器问题，两者不能互相替代。
4. 对组员交付先做目录、冲突、Mock、环境文件和公共区检查，再讨论业务合并。
5. 功能完成度、测试证据、演示脚本和答辩口径要放在同一仓库，避免“代码做了但无法证明”。
